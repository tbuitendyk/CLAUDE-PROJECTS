Classifier: a halt can no longer hide, and one blip no longer costs a day

tl;dr — three fixes are deployed and verified as of 05:45 UTC today. A halt now
shows on EVERY screen instead of one tab out of ten; a single dropped network
connection no longer latches a halt that blocks trading all day; and a fault
that is still happening now emails you every hour instead of once at the moment
it began. Today's 01:00 LONG was lost to exactly that combination. The box also
went unreachable separately around 01:35 and came back on its own by about
03:50 — it is armed, unhalted and reconciling cleanly now. Next entry
opportunity is Saturday 01:00 UTC. I also caught the deploy shipping the OLD
executor and fixed that before finishing; details below, because it is the kind
of thing that could bite again.

WHAT WENT WRONG, IN ORDER

On 29 October at 09:40:07 UTC the box lost one network connection to Binance.
Three things were written in that same second: it could not read the account,
it set a halt, and it stopped taking new entries. There was no retry — one
dropped connection was enough.

That halt was obsolete almost immediately. The same hour recorded five clean
account reads, and the box went on reading the account cleanly, five or six
times an hour, right through until the next day. The cause lasted one second.
The consequence lasted fifteen hours and twenty minutes, because a halt never
clears itself.

Nothing told you. The halt banner existed, but it was only drawn on one screen
— the LIVE subtab of Live Trading — and the page opens on Paper Books /
Greenlights by default. The Dashboard, Greenlights, Setups and Setup detail
screens showed no halt at all. On the mail side you got one message at 09:40
and then silence, because an ongoing fault only emailed on the moment it
started. So the first thing that could tell you was a trade failing to happen,
which is what you saw this morning.

Correction to something I told you earlier: I said the halt had been sitting
for about 40 hours. It was 15 hours 20 minutes. The 40 was my error and you
were right to doubt it.

Had the retry been in place, no halt would ever have been set, and the 01:00
LONG would have gone in on a box that was perfectly healthy at the time.

On the second one: entries are still blocked on any cycle where the account
could not be read. A retry must never buy a trade on a book we cannot see. What
changed is only that a brief failure no longer leaves a halt behind that needs
you to clear it.

THE DEPLOY ALMOST SHIPPED THE OLD CODE

Worth knowing, because it is a trap rather than a one-off. The script that
sends the executor to the box takes it from a SECOND copy that lives on the
vps-access branch, not from the authoritative file I had fixed. So the first
deploy ran, reported success, exited zero — and put the OLD executor on the
box. I only caught it because the script prints the fingerprint of the file it
sent, and I compared that against the expected one instead of trusting the
success message.

I updated the second copy, re-deployed, and confirmed the box is now running
the fixed version. But nothing in the system compares those two copies, so the
same silent-stale-deploy is possible on any future executor change. It is
written up as QC 197 with the fix I would propose — the deploy should REFUSE to
send a copy that disagrees with the recorded fingerprint. I have not built that;
it changes the deploy path and you have not approved one.
