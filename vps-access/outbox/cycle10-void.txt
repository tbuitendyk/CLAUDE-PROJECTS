WHAT GAVE IT AWAY

The worst scramble and the "real" arm printed the same number. Not close --
the same:

  real arm        -4703.229706986151
  scramble #10    -4703.2297069861515

That is 170 setups and about 30,000 trades landing on an identical total. It
is not a coincidence, it is the same computation twice.

THE BUG, WHICH I WROTE THIS MORNING

Yesterday I told you cycle 8 had wasted five hours because the job produced
19 scrambles and no real arm to compare them against. I fixed that by making
every multi-scramble job carry its own real arm, and said that enforcing it by
construction beat enforcing it by discipline.

The real arm signals "do not scramble me" by passing an empty value. The code
that decides how much to scramble each unit read, in effect, "if a value was
given, use it, otherwise use the run-wide default". An empty value is not a
value. So the real arm fell through to the run-wide setting and got scrambled
at exactly the same amount as scramble #10.

So the fix for a MISSING real arm guaranteed a FAKE one. Same file, same day.
No error, no warning, 3400 units of believable output.

The repair is that the code now asks whether the setting was SPECIFIED at all,
rather than whether it looks empty. A test asserts that, checks four
variations, and I watched it fail with the old code before trusting it.

THREE ASSUMPTIONS THIS KILLED (QC 38-40)

  38  "Empty means none." Against a fallback like that one it means "inherit
      the default" -- the opposite. Optional per-item settings are now
      resolved by whether the key is present, never by its value.
  39  "Zero failures means it ran correctly." Failure count counts CRASHES.
      Cycle 10: 3400 units, zero failures, void. That distinction has now
      mattered five times on this project.
  40  "A fix cannot introduce a fault." Cheapest guard available here: if any
      two arms come out bit-identical, the run is void. That is what caught
      this one, and it is now the standing check.
