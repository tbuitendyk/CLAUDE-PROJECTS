THE FIRST GAP — the money check that could not tell right from wrong

I reported that the Dashboard's cross-book check was non-discriminating: with
only one book on the test box, a total that wrongly mixes both books is the
same number as the correct one, so the check passed with the fault present.

Closed properly. The Dashboard's money calculation is now a named function
rather than buried in the drawing code, and a test RUNS it against a setup
holding a real book and a paper book at once — the one arrangement where right
and wrong give different answers. No real account can be in that state until
per-setup keys land, which is exactly why a test builds it. Drop the filter now
and four checks fail saying "counting positions from both books". The browser
check had passed on that same fault.

THE SECOND GAP — the browser had never seen your box's data

Rather than copy your live money down into a scratch container to look at, I
asked the deployed service to describe its SHAPES only — which fields exist, of
what type, how many rows — with every number replaced by its type. No figure of
yours was copied anywhere.

That comparison named the gap precisely. Your box has: an armed pilot, one open
short, thirty incidents, a closed trade. The test box had none of those. And
one state NEITHER box had ever produced: HALTED, with a reason.

That is the one worth your attention. The halt banner is where the "Clear the
halt" button lives, and the banner only appears while the box is halted — so no
browser had ever drawn that button. The path behind it was tested end to end on
the live box this morning, but the SCREEN it sits on was not. A control that
exists for an emergency, reachable only during that emergency, is the last one
you want to discover a fault in at the moment you need it.

Both states are now built as synthetic journals and driven through the real
page every run. The halted one checks that the banner appears, names the
recorded cause, offers the button, and that the button actually has a handler —
plus the reverse, that it is NOT offered when the box is healthy.

TWO MISTAKES OF MINE, CAUGHT BEFORE THEY REACHED YOU

Both were in the new checks, not the app, and both were false alarms on the
real-money screen — the worst kind, because they teach you to ignore warnings.

  * The outage check read the page's text and matched the banner's own SOURCE
    CODE, because this page's script sits inside the page. It fired on every
    healthy run.
  * Re-aimed at the banner's style class, it then matched the HALT banner,
    which shares that class — so it reported a broken screen in exactly the
    state it was written to verify.

Both found only because I re-ran each check against known-good state instead of
trusting that red-then-green meant it worked. The two banners genuinely did look
identical to a selector, so both pages now mark the outage banner explicitly.
