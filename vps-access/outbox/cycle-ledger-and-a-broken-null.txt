The processing cycle, the loop ledger, and a null that broke

tl;dr the seven-step cycle is read back below, verbatim as you gave it. Five
loops run so far, each with a one-liner and its code changes. The headline:
last night's null test came apart. Its six draws range from 14.7% to 91.2%,
and that spread is a fault in how I built the null, not a fact about the
market. I found the cause, fixed it, and tested the fix on real data. The
practical consequence is that cycle 1's 57.6% is neither confirmed nor
refuted -- it is unmeasured, and the next run measures it properly.


THE PROCESSING CYCLE (read back)

  1. Hypothesise. Look at everything learned so far and form the best
     available hypothesis about where to go next, always judged against
     maximum profit at the minimum possible risk.
  2. Decide the test. From that hypothesis, decide intelligently what should
     be tested next as the follow-up.
  3. Improve the platform. Analyse the software platform as it stands and
     independently implement whatever improvements the chosen direction
     needs. Do not bend the next experiment to fit yesterday's tooling.
     No code change reaches the environment without a standard email saying
     what was done.
  4. Script and launch. Script the settings into the VPS engine, start it,
     and form a real expectation of when it will finish -- five minutes,
     five hours or five days.
  5. Re-arm. If a job is not finished when checked, re-arm the check timer
     at an interval that matches how long it actually has left.
  6. Watch cheaply. Throughout 4 and 5, monitor for incoming mail
     continuously but as token-cheap as possible: one watcher, silent unless
     something real happens.
  7. Analyse hard, then loop. On completion, analyse thoroughly and think
     outside the box -- then return to step 1.

Range 14.7% to 91.2%. Each draw is 170 units, so the sampling error on any
one of them is about 3.5 points. A spread of 77 points is not noise.

I had pre-registered how to read this before firing it, and the rule was
explicit: if the draws disagree wildly with each other, the statistic is
unstable and needs fixing before it is used to decide anything. That is the
branch we are on. I am holding to it.

Worth saying plainly: L1's 57.6% sits comfortably INSIDE that spread, with
two draws above it. If I had run only rotation 0.143 I would have reported a
clean win. If I had run only 0.714 I would have reported the edge was dead.
Both would have been wrong, and both would have looked perfectly convincing.
That is the argument for error bars in one picture.


WHY IT BROKE

Edge is measured as: accuracy minus the majority baseline. The baseline is
"how often would you be right by always guessing the training window's most
common answer".

The null works by rotating the outcomes against the features, so any real
predictive relationship is destroyed while everything else is preserved. But
it rotated across the WHOLE series and only then cut the train / search /
holdout split, which is positional. So each rotation handed the holdout
window outcomes from a different stretch of market history -- and therefore
a different baseline.

I measured it on BTC/ZEC daily-3d over 908 chunks. Across seven rotations
the holdout baseline ranged from 0.265 to 0.419. The real, unrotated run sat
at 0.353 -- mid-pack.

A draw scored against a baseline 9 points softer clears "edge > 0" far more
easily with no change in skill whatsoever. So the pooled null was never one
null; it was a mixture over baselines. 57.6% cannot be compared against it
in either direction. Not as support, not as refutation.

One correction against myself: on a smaller sample I had this looking like
the real run faced the HARDEST baseline, which would have made L1 look
conservative and reassuring. It did not survive the larger sample. It is
mid-pack. I checked before believing it, which is the only reason that did
not end up in this email as a finding.


THE FIX

Rotate inside each window separately instead of across the whole series.
Each window then keeps its own set of outcomes exactly, so the band stays
put, every window's class balance stays put, and the baseline is identical
in every draw AND identical to the real run's. The feature-to-outcome
pairing is still destroyed inside each window, which is the entire job of
the null.

Verified on the same 908 chunks -- baseline across all seven rotations:

    before:  0.353  0.419  0.346  0.265  0.287  0.279  0.272
    after:   0.353  0.353  0.353  0.353  0.353  0.353  0.353

That is the property the test needed and did not have.

  2. Worker priority made provable. The health probe showed no classifier

     directly. The problem was that nothing could observe it. There is now a
     self-test that boots real workers and reads the kernel's own number for
     each thread. While in there I found a live bug: the pool's fallback
     path picked its function with a two-way guess, so any new kind of task
     would have quietly run the WRONG function and returned a
     plausible-looking object instead of failing.

Both are covered by tests that I verified actually fail when the thing they
protect is removed. Five deliberate breakages, five caught.


THE PATTERN, SINCE IT IS NOW FOUR IN A ROW

Every serious defect this week has been in the measurement, not the maths:
the API silently dropping two settings; the edge screen reading through a
money-ranked board; the read script that ignores which job you asked for;
and now a null whose draws were scored against six different yardsticks.

A broken sweep throws an error. A broken measurement hands you a number with
the right units and a plausible magnitude, and you build on it. The 91.2%
draw is the useful one here precisely because it is absurd -- it is too big
to rationalise. A defect that had shifted the null by five points instead of
seventy would still be in the system, and I would be writing you a confident
email about a real edge.
