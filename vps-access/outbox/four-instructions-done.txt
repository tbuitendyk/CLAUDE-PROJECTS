THE BUG, FIRST, BECAUSE IT AFFECTS WHETHER YOU CAN TRUST THIS CHANNEL

I had one script doing two jobs: checking for mail, and consuming it (marking
read, recording it as processed). The watcher ran that script on a timer and
only ever saw the few summary lines it greps for. So when your "Bluemail on
Android" and "While you're at it" emails arrived, the watcher noticed them,
consumed them, and I got two lines saying "VERIFIED" with no idea what they
said.

Detection and consumption must not be the same call. There are now two
scripts sharing identical verification logic:

  claude-mail-recent.sh   read-only. Changes nothing: no read flags, no
                          processed list. Reads ALL mail, not just unread, so
                          anything already consumed can still be recovered.
                          This is what the watcher runs.
  claude-mail-check.sh    the consuming one. Run deliberately, when messages
                          are actually going to be acted on.

I recovered all four of your emails through the read-only one. Nothing lost.
But it is the second time in an hour that my own tooling nearly silenced you,
so: if you send something and I do not respond, assume the plumbing is broken.

On #4, one thing worth knowing: the obvious way to write that is a single
"copy everything" command, which would double your mail every time it ran. On
your live mailbox that is a trap rather than a convenience, so it matches on
Message-ID and copies only what is genuinely absent. I ran it twice to prove
it: the second run reported copied=0, already-present=8, and the counts did
not move.

It also failed loudly on its first attempt rather than lying. It read zero
message-ids from a folder holding eight — doveadm prints the field name first,
so my pattern never matched — and reported "nothing to do" with a success
code. A backfill that silently does nothing looks exactly like a backfill that
worked. It now prints the counts it actually read and refuses to exit clean if
a non-empty folder yields nothing.
