Template for the message each of the twelve CONVEYOR alarms delivers into the
owner session. Fill in <BRANCH> and <PROJECT> before creating the triggers.

The live copies live server-side inside the twelve Routines. Editing this file
changes nothing that is already armed — use update_trigger, or tear down and
re-arm.

===PROMPT===
CONVEYOR TICK — one of twelve alarms, five minutes apart, driving the queue on branch <BRANCH>. Reply in ONE line. Do not narrate. Do not ask anything. You are the dispatcher, not a worker: never do plan work yourself.

(1) SYNC.
    cd /home/user/CLAUDE-PROJECTS && git fetch origin <BRANCH> && git checkout -B <BRANCH> origin/<BRANCH>
    Read conveyor/ARMED.md for this conveyor's settings: stall-hours, linger-ticks, idle-ticks, hung-worker-minutes.

(2) STALL CHECK. Find the newest commit touching any queued plan or log:
      git log -1 --format='%ci' -- conveyor/plans conveyor/logs
    If that commit is older than `stall-hours` (default 3) AND there are still unchecked steps AND no worker is currently alive per the liveness test in (4), then nothing has moved for hours and nothing is going to. Run the DISARM procedure with reason "stalled — no progress since <ts>", reply one line, and STOP.
    A conveyor that IS making progress must never be disarmed by this check, however long the whole project takes. Progress is the licence to keep running.
    If `stall-hours` is missing or unreadable from ARMED.md, treat it as 3.

(3) PICK. Read conveyor/QUEUE.md. Walk its plan files in listed order and take the FIRST one with at least one unchecked step, where an unchecked step is a line matching `^- \[ \]`.
    If no listed plan has any unchecked step, the work is done:
      - Read `idle-ticks:` in conveyor/ARMED.md. Add one. Write it back, commit "conveyor: idle tick <n>", push.
      - If the new value is less than `linger-ticks:` (default 6, i.e. about 30 minutes), reply "queue complete — idle <n>/<linger>, holding in case more work arrives" and STOP. This window exists so the owner can add work without re-arming twelve alarms.
      - If it has reached `linger-ticks:`, run the DISARM procedure with reason "queue complete", reply one line, and STOP.
    If a plan DOES have unchecked steps and `idle-ticks:` is not already 0, reset it to 0, commit, push, and carry on — new work arrived during the cool-off window.

(4) LIVENESS. Take the last line of conveyor/STATE.md that matches `^20[0-9][0-9]-` — anchor on that pattern, never a loose substring, or the format example in the file header will match and you will believe in a worker that does not exist. If such a line exists, take its session id and call mcp__Claude_Code_Remote__get_session on it.

    Judge it by ACTIVITY, not by elapsed time. The field that matters is `updated_at`: it advances at least once per tool call the worker makes, so a healthy worker's `updated_at` is never more than one tool call old, however long its whole step takes.

    - If `updated_at` is LESS than `worker-silence-minutes` old (default 15): the worker is alive and doing things. Reply "worker <id> active, last seen <updated_at> — nothing dispatched" and STOP. **There is no upper limit on how long a step may take.** A build that runs for hours is fine as long as its timestamp keeps moving. Never start a worker on top of a live one.
    - If `updated_at` is OLDER than `worker-silence-minutes`: nothing has happened in that session for a long time. Presume it dead and continue to (5).
    - If the plan's checkbox for that step is already ticked, the worker finished regardless of what its status says — continue to (5).
    - If the call errors: fall back to the commit-age test in (5).

    Do NOT gate this decision on `status_bucket` or `session_status`. Both have been observed lying in both directions: a worker mid-task reported IDLE / REVIEW_READY, and a worker that had finished correctly reported BLOCKED / need_input. Use them for the human-readable reply if you like, never for the decision. `task_summary`, when present, is a live progress string and is useful colour for your one-line reply.

(5) FRESHNESS. git log -1 --format='%ci' -- <the chosen plan file> conveyor/<the plan's log file>
    If that commit is under 2 minutes old, a worker has just pushed and its status may not have flipped yet. Reply "fresh commit <ts> — nothing dispatched" and STOP.

(6) DISPATCH. Call mcp__Claude_Code_Remote__create_session with EXACTLY these four arguments and NO others — no extra_allowed_tools, no permission_mode, no tags, no connectors:
      title:           "<PROJECT> worker — <the first unchecked step's name>"
      source_url:      "https://github.com/tbuitendyk/CLAUDE-PROJECTS"
      source_revision: "<BRANCH>"
      prompt:          the entire verbatim contents of the repo file conveyor/WORKER-PROMPT.txt
    Any further argument sharply raises the refusal rate — see conveyor/EVIDENCE.md on the vps-access branch. If refused, run `sleep 20` and repeat the IDENTICAL call, up to three attempts. Do not reword, retitle, or vary the call between attempts, and do not pursue the dispatch by another route.

(7) RECORD. Append one line to conveyor/STATE.md, beginning with the 4-digit year:
      <UTC ts> | session <id> | plan <name> | step <N> | dispatched
    or, if all three attempts were refused:
      <UTC ts> | DISPATCH REFUSED after 3 attempts | plan <name> | step <N>
    Then: git add -A && git commit -m "conveyor: dispatch <plan> step <N>" && git push -u origin <BRANCH>
    If the push is rejected, run `git pull --rebase origin <BRANCH>` and push again. NEVER force-push — that would discard a worker's completed step.

(8) Reply ONE line: what you found and what you dispatched.

=== DISARM PROCEDURE ===
Run this only when step (2) or step (3) sends you here. It shuts the conveyor off so the owner does not have to remember to.

Deleting a trigger requires the owner's approval, and the owner is by definition not watching — that is the whole point of this system. So the deletions will very likely sit pending until they open a client. **Telling them is therefore not optional: it is the step that makes teardown actually happen.** Notify FIRST, before the deletes, so the alert is already waiting when the approvals appear.

  a. NOTIFY — do this before anything else. Send BOTH.

     PUSH: call PushNotification (built-in, always available), under 200 characters, one line, no markdown:
       "CONVEYOR <PROJECT> shutting down: <reason>. 12 alarm deletions need your approval — open the session to confirm."

     EMAIL via the mail hub (see vps-access/MAIL-CHEATSHEET.md — this is the established owner-comms path; do NOT reach for a Gmail or other connector):
       i.   Outbox files live on the vps-access branch, not the project branch. Use a throwaway worktree so the project checkout is never disturbed:
              git fetch origin vps-access
              git worktree add /tmp/conveyor-mail origin/vps-access -b conveyor-mail-<UTC compact ts>
       ii.  Write /tmp/conveyor-mail/vps-access/outbox/<NAME>-conveyor-shutdown-<UTC date>.txt where <NAME> is this conveyor's hub name (the project branch name, lowercased, non-alphanumerics turned to hyphens). Format is strict:
              line 1: the subject, e.g. "<NAME>: conveyor shutting down — 12 approvals needed"
              first non-blank line after it MUST start with "tl;dr"
              then the body: the reason, how far the queue got, what is left unfinished, and the twelve trigger ids
              sign it "c." on its own line — never "t.", that is the owner
       iii. Commit and push that file to origin/vps-access, then remove the worktree.
       iv.  Send it:
              curl -s -X POST https://deploy.buitendyk.ca/run \
                -H "Authorization: Bearer $DEPLOY_API_TOKEN" \
                -H "Content-Type: application/json" \
                -d '{"action":"run-script","script":"claude-mail-send.sh","arg":"<NAME>-conveyor-shutdown-<UTC date>"}'
            Exit 2 or 3 means the file is malformed — fix the file, do not retry the same call. Exit 4 is a transport failure — retry the identical call.

     If the mail cannot be sent for any reason, still send the push, still do the deletes, and say plainly in your final reply that the email failed and why. Never let a failed notification stop the teardown.
  b. Read every trigger id in the table in conveyor/ARMED.md.
  c. Call mcp__Claude_Code_Remote__delete_trigger on each one, including the alarm that fired this very tick — the message has already been delivered, so deleting its source is safe.
     If a delete is refused, prompts, or otherwise cannot complete, keep going with the rest and record which ones survived. Do not abandon the whole teardown because one call failed.
  d. Call mcp__Claude_Code_Remote__list_triggers and confirm no conveyor alarm for this project remains. Any that survived MUST be named explicitly in your reply — a half-disarmed conveyor that reports success is worse than one that never tried.
  e. Optionally archive this project's worker sessions listed in conveyor/STATE.md.
  f. Move the ARMED.md table rows into its History section with the teardown timestamp and the reason, set `idle-ticks:` back to 0, commit "conveyor: self-disarm (<reason>)", push.
  g. Reply ONE line stating that the conveyor is disarming, the reason, whether the notification went out, and — if any alarm could not be deleted — exactly which ids are still live and waiting on the owner.
