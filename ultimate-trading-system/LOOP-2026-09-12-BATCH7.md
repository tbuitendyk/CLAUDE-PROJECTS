## S2 — the warning, and the rule caught my first criterion

**PASSES, at the second attempt, and the first attempt is worth recording.**

There is no line set anywhere. The coin's own periods are shuffled into a
different order two hundred times — the same coin with its trend taken away —
and the two numbers read off each shuffle. The question the screen answers is:
**could a coin with no trend at all, of exactly this length, have scored what
this coin scored?** If it could, the number is about the length and not about
the coin, and it is marked `cannot tell` with the range in the hover.

**My first criterion failed its own pre-registered check.** I first asked
whether the shuffles ever disagreed with each other at all — and at forty
periods two of two hundred did, so it passed a coin the rule said it had to
catch. Two answers out of two hundred is not a number that can tell anything
apart. The rule was written before the code and it caught the code, which is
exactly what it is for. I changed the criterion, not the check.

Measured on a coin with a real one-way run buried in it:

```
   40 periods | worst tail slice CANNOT tell (coin 0.000, shuffles 0.000-0.167)
  100 periods | worst tail slice CANNOT tell (coin 0.000, shuffles 0.000-0.308)
  300 periods | worst tail slice CAN tell    (coin 0.000, shuffles 0.103-0.289)
 2040 periods | worst tail slice CAN tell    (coin 0.000, shuffles 0.325-0.385)
```

And a coin with no trend at all is never tellable at any length, which is
right — there is nothing in it to tell.

The line lands between a hundred and a few hundred periods, worked out, never
written down. The test proves no number is typed: it reads the function's own
source and allows exactly one literal, the default count of shuffles, which is
a control on the screen like everything else here.

The shuffle is deterministic and pinned as such. Nothing this system reports
changes between two reads of the same data (RULE SEVEN).
